# CLICKCO — SPEC AUDIT

Cross-consistency audit of the seven `docs/clickco-*` files. Performed as a read-only review; no application code was written and none of the audited files were edited.

Scope audited:
- `clickco-v0.2-locked-spec.md`
- `clickco-terms-conditions-v2.md`
- `clickco-01-design-pipeline.md`
- `clickco-02-repo-architecture.md`
- `clickco-03-claude-code-build-plan.md`
- `clickco-04-schema.sql`
- `clickco-05-pricing-engine.md`

BLOCKER = code cannot be written correctly without a decision. MAJOR = will produce a real bug, dispute, or legal exposure if uncorrected, but has a workable interim reading. MINOR = inconsistency worth fixing for hygiene; unlikely to cause an incident on its own.

|---|---|---|---|---|---|
| SA-01 | MAJOR | T&C↔Schema coverage | T&C §8.2, schema §12/§16 | T&C §8.2 lets Clickco claim against a client for equipment damage "supported by documentary evidence of the damage and its cost," but no table anywhere in the schema records an equipment-damage claim (payee, incident, evidence, amount, resolution). `disputes` is chargeback/billing/conduct/delivery-shaped (see its `kind` comment) and doesn't fit; `quality_escalations` is about photo/video output quality, not gear damage. §16 (deferred items) does not list it either — it was simply never scoped. | Add an `equipment_claims` table (or extend `disputes.kind` with `EQUIPMENT_DAMAGE` and add `evidence`/`claim_amount_paise`/`documentary_evidence` fields sufficient to support §8.2) before Sprint 9-10 (admin panel, where this would be adjudicated). |
| SA-02 | MAJOR | T&C↔Schema coverage | T&C §12, schema §12/§16 | T&C §12 (Grievance Redressal) is a hard legal requirement under the Consumer Protection (E-Commerce) Rules 2020: complaints acknowledged within 48h, resolved within 30 days. The schema has no `support_tickets`/`ticket_messages` — explicitly deferred at §16 — and no field anywhere tracks a grievance's received-at/acknowledged-at/resolved-at against the 48h/30-day clocks. `disputes` and `quality_escalations` are booking-scoped and don't cover a generic non-booking grievance (e.g. a data-deletion request under §11.4, or a complaint about the Grievance Officer process itself). | Either (a) scope `support_tickets` into an earlier sprint than "with the admin panel spec" given it is a compliance requirement, not a nice-to-have, or (b) explicitly widen `disputes` to be the grievance surface and add the acknowledgement/resolution SLA fields. Flag this as pre-launch-blocking, not post-launch, since Grievance Officer disclosure is also required for app store approval (v0.2 G-31, G-45). |
| SA-03 | MAJOR | Money / type safety | `clickco-02-repo-architecture.md` §3, `clickco-04-schema.sql` §11 | `packages/contracts` types every monetary field as `z.number().int()` (a JS/TS `number`, safe only to 2^53-1 ≈ 9.007×10^15). The schema stores money as Postgres `bigint` (64-bit, max ~9.2×10^18). For Clickco's actual transaction sizes (₹thousands–₹lakhs in paise) this will never overflow in practice, but it is a real type-safety gap: nothing stops a future ledger aggregate, a payout-batch total, or an adversarial input from exceeding `Number.MAX_SAFE_INTEGER`, and Zod's `z.number().int()` will not catch it — it will silently produce a corrupted value via float rounding. | Change `packages/contracts` money fields to a bigint-safe representation — `z.coerce.bigint()`, a branded string-encoded integer, or `z.number().int().safe()` with an explicit application-level ceiling well under 2^53 documented as a hard business rule. Cheapest fix: keep `z.number().int()` but add a runtime `MAX_SAFE_MONEY_PAISE` guard at the API boundary and document why it's safe, or switch to bigint end-to-end. |
| SA-04 | MINOR | SLA / emergency band | `clickco-v0.2-locked-spec.md` §8, `clickco-04-schema.sql` §1, `clickco-05-pricing-engine.md` §5 | v0.2 §8's emergency table lists only 4 rows (<3h, 3–8h, same day, next day) with no explicit ">48h / not emergency" row. The schema's `emergency_band` enum and doc 05's rate table both correctly include a 5th band, `NONE` (>48h, 1.00×, standard 50/50), which v0.2 simply omits because it wasn't the focus of that section. Not a contradiction — v0.2 is describing "the emergency tier" specifically, and NONE isn't emergency — but a reader cross-checking "five bands" (as this audit's brief assumed) will initially see only four in v0.2. | No action required; this is complete coverage under a different framing. Optionally add a one-line note in v0.2 §8 clarifying that `NONE` (>48h, standard pricing) is the implicit fifth/default band, to pre-empt the same confusion in a future reader. |
| SA-05 | MINOR | Terminology | `clickco-terms-conditions-v2.md` §2.6 vs `clickco-v0.2-locked-spec.md` §9 | Both use "15 minutes" but for two different clocks that a fast reader could conflate: T&C §2.6's 15-minute grace is *waiting-time billing* (client not ready when the photographer arrives on time) starting a chargeable-waiting clock. v0.2 §9's 15 minutes is the *no-show escalation* trigger (photographer hasn't checked in by scheduled_start+15, triggering SMS/call/ops-alert/emergency-broadcast). | SA-06 | MINOR | Rate card | `clickco-01-design-pipeline.md` Screen 2/8, `clickco-05-pricing-engine.md` §5/§8 | Screen 2 and Screen 8 mockup copy show a Professional-tier extension price of "+₹3,800 per extra hour." Professional base at Surat (TIER_1) is ₹4,250/hr. ₹3,800 does not equal ₹4,250 × any of the documented category uplifts (1.00–1.25×) — the nearest match would require an uplift of ~0.894×, which doesn't exist. It also isn't ₹4,250 × Food's 1.15× (=₹4,887.50) or any tabulated value. | This is a genuine numeric mismatch, not a design placeholder — flag for correction. | SA-07 | MINOR | Documentation only | `clickco-terms-conditions-v2.md` §5.1 vs `clickco-v0.2-locked-spec.md` §6 | T&C §5.1 defines the delivery window as running from "whichever is later" of (photographer check-out, full payment received). v0.2 §6 implements this with a single T0 (=CHECKED_OUT) plus a *paused* clock during `BALANCE_PENDING` rather than a literal "later of two start points" — these are mathematically equivalent (a clock that starts at A and pauses until B is met produces the same due date as a clock that starts at max(A,B)) but described in different mental models across the two documents. | No functional change needed — confirmed equivalent on inspection — but worth a one-line note in DOMAIN.md (added, see below) stating the equivalence explicitly so a future implementer doesn't try to literally implement "whichever is later" as a second SLA anchor timestamp alongside the existing pause mechanism, which would double up the logic. |

**Areas checked and found clean** (no findings):

- **A. State machine** — the 24-value `booking_status` enum (schema §1) and the v0.2 §6 lifecycle diagram, including all 8 exception/terminal states (CANCELLED_CLIENT, CANCELLED_PRO, PRO_NO_SHOW, ACCESS_DENIED, UNSAFE_SITE, DATA_LOSS, QUALITY_ESCALATION, ABANDONED), match exactly in both directions. No orphans.
- **B. Money** — every monetary column in the schema is `bigint … _paise`; the only `NUMERIC`/`DECIMAL` columns found are non-money (hours, distances, radii, a rank score) — confirmed by grep across the whole file. Percentages are consistently `integer … _bps` (basis points) throughout pricing and payout tables.
- **F. Emergency bands** — the 5 bands (NONE, NEXT_DAY, SAME_DAY, HOURS_3_8, HOURS_UNDER_3), their multipliers (1.00/1.20/1.40/1.80/2.20×), guarantee status, and capture behaviour (100% upfront for SAME_DAY/HOURS_3_8, authorise-only for HOURS_UNDER_3 with 90-min auto-refund) are identical and cross-referenced explicitly across v0.2 §8, doc 05 §5, T&C §3.7, and the `emergency_multipliers` table — doc 05 §5 literally cites "Doc v0.2 §8 and T&C §3.7 describe the same behaviour — this is where it's enforced."
- **G. T&C↔schema coverage (the four items that DO have columns)** — peak season (T&C §3.2) → `festival_calendar.is_peak_season` ✅; 15-minute waiting grace (T&C §2.6) → `extension_rates.waiting_grace_minutes` ✅; retention (T&C §5.4) → `media_assets.purge_after` with the correct 7-day RAW / 30-day JPEG split, both measured from delivery ✅; promotional opt-in (T&C §9.4) → `users.promo_use_consent` + `promo_consent_at`, with a CHECK constraint enforcing the timestamp is set whenever consent is true ✅. (Equipment liability cap and Grievance Officer coverage are the two gaps — see SA-01, SA-02.)
- **Retention (E)** — RAW = delivery+7d, JPEG = delivery+30d, consistently measured from delivery (never shoot) across v0.2 §2/§3.4/§5, T&C §5.4, and `media_assets.purge_after` semantics plus `sla_kind` (`RAW_PURGE`, `JPEG_PURGE` both keyed off "delivered+").
- **Rate card headline figures (C)** — Basic ₹3,500 / Semi-Pro ₹5,500 / Professional ₹8,500 / Expert ₹14,000 (all at 2-hour minimum, Surat/TIER_1) match exactly between doc 05 §5's `base_rates` table and every headline figure in doc 01's Stitch prompts and v0.2. (The one mismatch found is the Professional *extension* rate, not the headline price — see SA-06.)
- **SLA clock ladder (D)** — the `sla_kind` enum, v0.2 §7's implicit ladder (T0+2h upload start, +48h delivery due, delivered+7d RAW purge, delivered+30d JPEG purge/link revoke), and T&C §5 delivery commitments describe the same timings. T0 is CHECKED_OUT everywhere it is explicitly named, never booking creation — confirmed in schema comment, v0.2 §6, and doc 03's `domain-guardian` agent spec (which explicitly checks for this violation).

## Summary

- **BLOCKER: 1** (SA-11, found 21 Oct 2026 by the migration integration test; patched)
- **MAJOR: 9** (SA-01, SA-02, SA-03, SA-13, SA-14, SA-15, SA-16, SA-21; SA-15–21 found 24 Oct 2026 designing S8)
- **MINOR: 9** (SA-04, SA-05, SA-06, SA-07, SA-12, SA-17, SA-18, SA-19, SA-20)

No blocking internal contradictions were found — the spec set is unusually well cross-referenced for a first pass (doc 05 explicitly cites doc v0.2 and the T&C by section number in several places, which is why so few real conflicts turned up). The three MAJOR items are all coverage gaps (T&C clauses with no corresponding schema surface, or a latent type-safety gap) rather than the documents disagreeing with each other. None of them require a business decision to fix — they're schema/type additions — which is why none are rated BLOCKER despite being real.
